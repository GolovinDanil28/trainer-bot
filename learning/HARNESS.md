# Harness: что это и как применить здесь

Термин пришёл из обсуждения 19.10.2026. В разных источниках его понимают
по-разно; здесь — рабочее определение для этого хаба.

## Определение

**Harness** — это обвязка вокруг модели, которая превращает модель в
*инструмент*: даёт ей роли, инструменты, память, правила, цикл обратной связи
и способ проверки результата.

Модель — это двигатель. Harness — это машина целиком: руль, приборы, ремни,
подвеска и маршрут.

## Из чего состоит harness

| Слой | В OpenCode V2 это | У нас |
|---|---|---|
| Роли | `.opencode/agents/*.md` | 5 агентов: tutor, planner, implementer, reviewer, researcher |
| Процедуры | `.opencode/skills/*/SKILL.md` | 3 скилла: learn-by-doing, spec-first, socratic-debug |
| Точки входа | `.opencode/commands/*.md` | `/spec`, `/teach`, `/retro`, `/status` + 6 команд OpenSpec |
| Правила | `AGENTS.md`, `opencode.json` → `permissions` | общие правила + матрица разрешений |
| Автоматизация | `.opencode/plugins/*.ts` → хуки | `guardrails.ts`: spec-gate, shell-guard, audit, teach-hint |
| Контракты | `openspec/` | спеки как единственный источник правды о поведении |
| Память | `learning/LOG.md`, `knowledge/` | журнал обучения + база знаний |
| Проверка | тесты + `reviewer` | тест на пункт задачи + ревью против требований |

## Почему «обёртка» — это не надстройка, а ядро

Модель без harness:
- не знает, что у неё есть проект;
- не знает, какие правила действуют;
- не знает, что считать «готово»;
- не проверяет себя;
- не помнит, что выяснила в прошлой сессии.

Именно эти девять пробелов закрывает обвязка. **Харнесс — это и есть обучение:**
ты не изучаешь «магию промптов», ты собираешь среду, в которой модель
становится предсказуемой, а себя — читающим её решения.

## Что ещё можно добавить (когда понадобится)

Не строить заранее. Список — чтобы было из чего выбирать:

1. **Evaluator-агент.** Отдельный агент, который оценивает работу по шкале
   (полнота спеки, покрытие тестами, читаемость). Даёт обратную связь, которую
   тебе самому тяжело дать себе.
2. **Session-scoped правила.** `ctx.session.update({ permissions })` — менять
   права внутри сессии: например, в «обучающем» режиме запретить агенту
   редактировать файлы без твоего подтверждения, а в «скоростном» — разрешить.
3. **HTTP-хуки.** `session.hook("http.request")` — например, принудительно
   снизить `temperature` для ревьюера, чтобы он не «фантазировал».
4. **MCP-серверы.** Внешние инструменты (база знаний, задачник, почта).
   Подключать, когда появится реальный потребитель, а не «на будущее».
5. **Скрипты-харнесс.** Твои собственные CLI-обёртки (`make plan`, `make check`),
   которые агент зовёт через `shell`. Это даёт воспроизводимость: одну команду
   — один результат, а не «модель так решила».
6. **Снапшоты и форматирование.** Встроены в OpenCode — включить и не изобретать
   своё.

## Правило

Каждый новый слой харнесса обязан **заменять ручной ритуал**, а не добавлять
поверх. Если агент всё ещё может сделать что-то «не по правилам» — значит,
правило живёт только в голове, а это не работает.

Проверка: спроси себя «что я теперь делаю руками, чего раньше делал руками?»
Если ответ «ничего» — слой нужен. Если «то же самое, но с дополнительным шагом» —
удаляй.
