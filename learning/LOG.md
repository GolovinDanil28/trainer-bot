## Записи

### 24.10.2026 — Первая реализация по спеке: расписание и время

**Делали:**
- разбили MVP на два change'а и написали спеку `trainer-bot-schedule`
  (13 требований, 3 капабилити);
- подняли каркас: venv, pytest, ruff, `pyproject.toml`, конфиг на
  `pydantic-settings`, SQLite с WAL и внешними ключами;
- сделали домен: разбор `/new`, тексты ответов, расчёт момента напоминания
  с переходами на летнее время, окно тика;
- подключили модели, репозиторий и тонкие хендлеры; закрыли 11 задач из 22.

**Решения:**

| Решение | Альтернативы | Почему выбрали |
|---|---|---|
| Два change'а вместо одного | одна спека на весь v1 | правила «самочувствие → план» ещё не придуманы, мешать их с расписанием вредно |
| Тик 30 с, состояние в БД | job на каждое напоминание | перезапуск не теряет будущие напоминания |
| Фиксированные типы тренировок | свободный текст | по строке нельзя считать правила плана |
| Длительность по умолчанию по типу | спрашивать в `/new` | в R-01 длительности нет, а в R-07 она нужна |
| Мастер кнопок — отдельный change | встроить в текущий | текущий change закрывается, не разрастаясь |
| Отмена `pending` → задача 4.6 | поднять модель `reminder` в 2.4 | таблица появляется там, где есть доставка |

**Что понял:**
- Спека ловит невыполнимые задачи **до** кода: 1.4 и 2.4 оказались
  противоречивыми на бумаге, а не после написания кода.
- Время нельзя хранить «как есть»: в базе только UTC, а «Пн 19:30» — это
  правило, из которого момент вычисляется. Иначе переход часов сдвигает всё
  расписание.
- Тест `utcoffset()` у UTC-дататайма всегда возвращает ноль — проверять надо
  смещение **после** `astimezone`, иначе тест проходит вхолостую.

**Что осталось непонятным:**
- как APScheduler ведёт себя при пропущенном тике (машина спала) — тема
  для следующего `/teach`;
- чем платить за `check_same_thread=False` и WAL, когда запросов станет много.
