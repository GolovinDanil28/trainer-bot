# Tasks: trainer-bot-multiuser-foundation

## 1. Схема и миграция

- [x] 1.1 Таблица `user` (telegram_id unique, tz, wellness_time, week_review_time,
  is_active) и `user_id` в `workout`, `wellness`, `plan_snapshot`,
  `weekly_report`. Уникальности: `wellness (user_id, day)`,
  `plan_snapshot (user_id, plan_date)`, `weekly_report (user_id, week_start)`.
  Проверка: DDL на чистой базе; второй пользователь пишет самочувствие за тот же
  день. (R-41, R-42)
- [x] 1.2 Цели `ON CONFLICT` в `claim_wellness_prompt`, `save_wellness`,
  `save_plan_snapshot`, `claim_weekly_report` переезжают на составной ключ
  вместе с ограничениями. Проверка: тик самочувствия и снимок плана работают
  после смены схемы (иначе `OperationalError`).
- [x] 1.3 Миграция существующей базы одной транзакцией: прочитать данные,
  пересоздать схему, вернуть строки с `user_id`; пустой `claimed_at`
  заполняется. Проверка: полная старая схема (8 таблиц) сохраняет число строк,
  вариант без колонки `claimed_at`, повторный запуск. (R-43)
- [x] 1.4 Создание владельца из `OWNER_ID` при старте, идемпотентно;
  настройки пользователя берутся из конфига.
  Проверка: два старта — одна строка, настройки сохраняются. (R-41)

## 2. Доступ и изоляция

- [x] 2.1 `access.py`: `owner_only` → «только зарегистрированный»; текущий
  пользователь определяется по `effective_user.id`. Проверка: посторонний
  получает отказ на командах и на свободном тексте. (R-41, R-18)
- [x] 2.2 Репозиторий: все выборки и записи принимают `user_id`; чужие строки
  не находятся (`/off` чужой тренировки → «не найдена»). Проверка: парные
  тесты «свой видит, чужой нет» на тренировки, историю, самочувствие,
  снимки, разбор. (R-42)
- [x] 2.3 Сервисы и хендлеры передают пользователя; снапшот для модели —
  только свои тренировки. Проверка: свободный текст второго пользователя не
  содержит тренировок первого. (R-42)
