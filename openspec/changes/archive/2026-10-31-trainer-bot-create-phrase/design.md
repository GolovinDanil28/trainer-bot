# Design: trainer-bot-create-phrase

### D1. Две величины храним, пересчёт только при создании

`distance_km` (nullable) и `duration_min` — оба поля в `Workout`. Дистанция —
для отображения, минуты — для правил плана (`LIGHT_SCORE → 70 %`).

**Почему не пересчитывать потом:** получились бы две правды, из которых одна
молча устаревает — тот же класс ошибки, что «70 %», зашитый текстом в карточку.
Пересчёт один раз на входе; дальше значения живут своей жизнью. Правило плана
только в минутах — доказано фактом: `core/plan.py` не знает тип тренировки.

### D2. Модель достаёт токен даты, дата решает только код

Модель возвращает `date_raw` («сегодня», «завтра», «28.10»), а
`core.resolve_date(date_raw, today)` превращает его в реальную дату в таймзоне
владельца. Модель НЕ считает даты: она не знает ни сегодняшнего числа, ни
таймзоны, и её «завтра» — то самое место, где все ошибаются с временем
(§8.4). Резолв детерминирован и проверяется тестами с фиксированным `today`
(§9). Время (ЧЧ:ММ) модель уже достаёт сегодня — токен даты ложится в тот же
слой работы.

### D3. Свободный тип: правим промпт, а не расширяем список

Промпт теряет требование «тип словом из списка» и получает правило: верни тип
короткой фразой (1–3 слова), если владелец назвал вид спорта. Проверка формы —
в коде: не пусто, не длиннее 32 символов, без markdown-символов; модель
находит «интервальный бег», код решает, годится ли он как тип.

**Колонка `workout_type` растёт с 16 до 32 символов** — «интервальный бег»
занимает ровно 16, и граница не должна служить рисунку слоёв, а должна
служить владельцу.

### D3a. Проверка опоры для дат смотрит на текст, а не на токены

Наивная проверка «токен есть среди слов» ломается на «28.10»: точка — не часть
слова, и дата не находится. Поэтому для даты сравнивается нормализованная
строка целиком (`text.lower().replace("ё","е")` с схлопнутыми пробелами), а для
типов остаётся проверка по словам. Это нашёл ревьюер: сценарий «Формат даты»
был недостижим из чата, хотя unit-тесты резолва проходили.

### D4. Уточнение — состояние в памяти bot-слоя

`PendingChoice(chat_id, intent, created_at)` в dict процесса бота. Telegram
присылает `callback_query` → выбор → создание. Не в БД: потеря уточнения при
рестарте («попроси заново») стоит меньше, чем таблица для временного
состояния — у зависимостей уточнения нет тишиных эффектов, их нечему
восстанавливать.

Ключ кнопки: `choice:<pending_id>:<index>`; `index` выбирает вариант из
запомненного intent. Срок годности — 10 минут, проверяется при обработке.

**Прецедент:** кнопки 1–5 самочувствия; механика `CallbackQueryHandler` уже
заведена, новый handler не ломает порядок (`§8`, «bot может использовать core»).

### D5. Разовая тренировка — колонка `date_once` в `Workout`

Не новая таблица: разовая тренировка — это та же тренировка, у которой
заполнена `date_once`, а `schedules` пуст. Час напоминания = (date_once,
time из фразы). `/list` показывает активные разовые (дата ≥ сегодня);
напоминания по разовым считаются в тике отдельными строками (не по weekday)
и проходят через тот же `claim_reminder` — ключ
`(workout_id, scheduled_at)` работает без изменений (§8.5).

Миграция: `create_all` не добавляет колонки, поэтому добавляется минимальный
шаг `apply_migrations(engine)`: `pragma table_info` + `ALTER TABLE ADD COLUMN`,
идемпотентно. Механизм версий не заводится: две добавки — функции, а не
фреймворк (§8.2).

### D5a. Миграция — только для SQLite и только добавления колонок

`apply_migrations` делает `PRAGMA table_info` + `ALTER TABLE ADD COLUMN`.
Это честно для v1 (SQLite — единственный движок) и для не-SQLite является no-op:
другие движки мигрировались бы инструментом, а не pragma-проверкой. Длина
`VARCHAR` в SQLite не проверяется, поэтому `workout_type` 16→32 существует
только в модели; для старых баз это не ломает данные.

### D6. Инкременты делят риски, а не сам change

1. дистанция + свободный тип (промпт, валидация, миграция колонок, `/list`);
2. уточняющие кнопки (состояние уточнения, обработчик);
3. разовая тренировка (резолв даты, миграция `date_once`, тик, план).

Каждый инкремент закрывает свои требования (R-32/R-33 → R-34 → R-35) с тестами,
но мерж один, в конце: цикл «один change = один merge» не меняется.

## Risks

- **[Модель отказывается от «бег»]** — самое вероятное место всей фичи:
  правка промпта с примером «бег по средам в 19:00 → create» и живой тест
  под `RUN_OLLAMA_TESTS=1`. Если qwen2.5 упрётся и вернёт `none` — откат:
  список типов остаётся, к нему явно добавляются «бег», «интервальный бег».
- **[«28.10» без года двусмысленно]** → правило: без года это ближайшая такой
  даты в будущем (уже прошедший день означает следующий год). Тест с
  фиксированным `today` ловит ровно это правило.
- **[Кнопка умерла в воздухе]** → если callback пришёл, а уточнение уже
  истёк или отсутствует — бот отвечает подсказкой, а не молчит.

## Границы (не в этом change)

- План НЕ учитывает дистанцию при уменьшении: уменьшаются только минуты
  (правило не переписывается, риск ложной умности).
- «бег или …» уточняется один раз; цепочка вопросов «а время?» не строится.
- Разовая тренировка не повторяется и не превращается в недельную автоматически.
