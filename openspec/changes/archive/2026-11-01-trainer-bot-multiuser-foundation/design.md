# Design: trainer-bot-multiuser-foundation

### D1. Владелец данных — `user`, для тренировки; остальное наследует

`user_id` есть только у `workout`, `wellness`, `plan_snapshot`,
`weekly_report`. `schedule`, `reminder`, `checkin` наследуют владельца через
тренировку: дублировать поле в них — значит завести вторую правду, которая
разойдётся. Все запросы к наследникам идут с join на `workout.user_id`.

Цена — join в каждом запросе; выигрыш — нельзя создать напоминание от одного
пользователя на тренировку другого.

### D2. Инвайт-код появится позже, и это осознанно

Здесь не открываем регистрацию: change делает данные безопасными для нескольких
пользователей, но вход по-прежнему один. Так прод не ломается: владелец
создаётся автоматически, данные мигрируют, поведение не меняется. Регистрация
по коду — следующий change вместе с тиками по пользователям.

### D3. Миграция пересоздаёт таблицы с UNIQUE

SQLite не умеет `ALTER ... DROP CONSTRAINT`. Для `wellness`,
`plan_snapshot`, `weekly_report` миграция: создать новую таблицу с составным
UNIQUE → `INSERT ... SELECT` с `user_id` владельца → drop старой → rename.
Всё в одной транзакции; повторный запуск безопасен (проверка по `pragma
table_info` и наличию колонки). Данные не теряются — это единственное, что
нельзя восстановить из кода.

### D3a. Уникальность и `ON CONFLICT` меняются вместе

Первый заход на миграцию показал связанность, которую легко пропустить:
`claim_wellness_prompt`, `save_wellness`, `save_plan_snapshot` и
`claim_weekly_report` вставляют строки через `ON CONFLICT` по глобальному ключу
(`day`, `plan_date`, `week_start`). Как только уникальность становится
составной (`user_id, …`), эти `ON CONFLICT` перестают совпадать с ограничением
и падают с `OperationalError`.

Значит схему нельзя менять отдельно от кода: в одном шаге идут колонка
`user_id`, составной уникальный ключ, цель `ON CONFLICT` и передача
пользователя во все вызовы. Это причина, по которой change оценивается
в 6–8 часов, а не в два.

### D3b. Текущий пользователь — contextvar, а не параметр

Сервисы — синглтоны, а пользователь приходит с обновлением Telegram. Поэтому
`db/context.py` держит `ContextVar` с владельцем, декоратор `registered_only`
объявляет его через `acting_as`, а `repository._owner()` берёт оттуда. Это
осознанный компромисс: меньше шума в подписях, но забытый владелец не падает,
а пишет «за первого». Защита — `user_id NOT NULL` в схеме и отдельный
пользователь по умолчанию только для тестов; тесты изоляции обязательны.

### D3c. Миграция — одна транзакция, NULL-значения чинятся на входе

Черновик миграции терял данные: `weekly_report.claimed_at` мог быть NULL,
вставка падала после DROP. Обернуть всё в `engine.begin()` не помогло: pysqlite
коммитит DDL (DROP TABLE) независимо от транзакции — проверено тестом, который
рвёт миграцию посередине. Поэтому перед миграцией снимается копия файла базы,
при сбое она возвращается на место, а после вставки число строк каждой таблицы
сверяется с исходным. Тест — на всех восьми таблицах, варианте без колонки
`claimed_at` и на принудительном сбое.

### D4. Доступ: зарегистрированный, а не «владелец»

`owner_only` переименовывается в `registered_only`: проверка «этот telegram id
есть в users». `OWNER_ID` остаётся только для создания первого пользователя и
для инвайт-кода в следующем change'е, а не для доступа к данным.

### D5. Настройки пользователя — в строке, не в конфиге

`tz`, `wellness_time`, `week_review_time` переезжают в `user`. Настройки из
конфига становятся значениями по умолчанию для первого пользователя. Иначе
второй человек не сможет жить в своей таймзоне.

## Risks

- **[Утечка данных между пользователями]** → парные тесты на каждый запрос;
  изоляция проверяется как сценарий, а не как «код выглядит правильно».
- **[Миграция съест данные]** → одна транзакция, тест на копии реальной схемы
  с данными, идемпотентность.
- **[Сломанный прод во время миграции]** → change не открывает вход, поэтому
  единственный пользователь — владелец; откат = восстановление файла базы.
- **[Тики пока одного пользователя]** → это следующий change; здесь явно
  записано, что многопользовательский планировщик ещё не сделан.
- **[`ON CONFLICT` со старой целью]** → все вставки-«занять день/неделю»
  обязаны переехать на составной ключ в том же коммите; иначе первый же тик
  падает на `OperationalError`.
