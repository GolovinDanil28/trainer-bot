# Design

## Context

В боте восемь команд и свободный текст через Ollama. `/start` не зарегистрирован,
free-text фильтр отсекает команды, поэтому первый контакт с ботом — тишина.
Справка нужна как **вход**, а не как ещё одна функция: она обязана работать,
когда модель недоступна, и не должна расходиться с реальным набором команд.

Ограничения: `core/` не знает про Telegram (§8.1); тексты для пользователя живут
в `core/messages.py`, а данные карточки (команды, фразы, примеры) — в
`core/help.py`, потому что из них текст собирается; доступ проверяется одним
декоратором `owner_only`; требования — `specs/trainer-bot-help/spec.md`,
мотивация — `proposal.md`.

## Goals / Non-Goals

**Goals:**

- Одна карточка, два входа: команда и фраза.
- Список команд — данные, а не строка в тексте: добавление команды не требует
  правки справки.
- Справка не ходит в модель и не пишет в базу.

**Non-Goals:**

- Интерактивное меню, кнопки, постраничная справка.
- Подсказка по отдельной команде.
- Проверка «README не отстаёт от кода» автоматически — только вручную.

## Decisions

### D1. Триггеры справки проверяются до модели и по полному совпадению

`is_help_request(text)` живёт в `core/help.py` и вызывается в `on_free_text`
**до** `AssistantService`. Сравнение — по нормализованной строке (нижний регистр,
`ё → е`, убрать пунктуацию по краям и внутри, схлопнуть пробелы) с фиксированным
набором фраз.

**Почему полное совпадение, а не подстрока:** «помоги составить тренировку на
среду» — это запрос к ассистенту, а не просьба о справке. Подстрока «помоги»
украла бы фразу у модели и вернула карточку вместо действия.

**Альтернатива (отвергнута):** отдать распознавание «помоги» модели. Тогда
справка не работает при выключенной Ollama (R-30), стоит 2 секунды и может
вернуть не то — ровно в тот момент, когда человек просит помощи.

**Альтернатива (отвергнута):** включить триггеры в промпт как `action: help`.
Это тот же отказ от детерминизма плюс правка контракта модели ради текста,
который не зависит от ввода.

### D2. Список команд — данные в `core/help.py`

```python
@dataclass(frozen=True, slots=True)
class CommandHelp:
    command: str      # "/new"
    purpose: str      # "создать тренировку"
    example: str      # "/new strength Пн,Ср,Пт 19:30"

COMMANDS: tuple[CommandHelp, ...] = (...)
FREE_TEXT_EXAMPLES: tuple[tuple[str, str], ...] = (...)
```

`format_help()` в `messages.py` рендерит карточку из этих данных. Один источник
правды: карточка и тест на дрейф используют один и тот же `COMMANDS`.

**Почему не строка в `format_help`:** строка расходится с кодом молча. Именно так
в прошлом change мы получили README, который врал про количество задач.

**Альтернатива (отвергнута):** генерировать справку из `application.handlers` в
`app.py`. В `core/` нет доступа к Telegram-приложению, а тянуть его туда —
нарушение §8.1. Тест на дрейф решает ту же задачу, не ломая слои.

### D3. `/start` = приветствие + та же карточка

`format_start()` = строка приветствия + `format_help()`. Два текста, один
источник содержимого.

**Почему:** первое сообщение в чате должно и здороваться, и объяснять. Держать
две независимые карточки — гарантированное расхождение через месяц.

### D4. Справка закрыта владельцем

`/start` и `/help` — с `@owner_only`, фраза-триггер проверяется после
`is_owner` в `on_free_text`. Это тот же R-05/R-18/R-22, повторённый для новой
капабилити: у бота один пользователь, и «личный бот» не должен рассказывать
посторонним, что он умеет.

**Альтернатива (отвергнута):** открытая справка для всех. Она не раскрывает
данные, но ломает единое правило доступа и создаёт второй класс команд, которые
надо помнить при каждой новой фиче.

### D5. В карточке честно перечислены ограничения

Раздел «Чего не умею» перечисляет: разовые переносы, тренировку на конкретную
дату (появится отдельным change), несколько действий в одной фразе, недельный
разбор, работу свободного текста без Ollama.

**Почему:** карточка — обещание. Если она молчит об ограничении, пользователь
считает это багом. Когда появится разовая тренировка, этот раздел обязан
измениться — это ручная проверка при ревью, тестом не ловится.

### D6. Тест на дрейф

Тест собирает команды, зарегистрированные в `build_application`, и сравнивает с
`{entry.command.lstrip('/') for entry in COMMANDS}`. `start` и `help` входят в
`COMMANDS` явно — карточка должна упоминать и себя.

**Почему включаем `start`:** иначе тест пришлось бы ослабить до «все, кроме
start», и новая команда могла бы спрятаться в исключении.

Тест дополнительно требует, чтобы в приложении был ровно один `MessageHandler` и
это был `on_free_text`: иначе команду можно зарегистрировать не как
`CommandHandler`, а регуляркой в `MessageHandler`, и тест этого не заметит.

**Известное ограничение:** `PrefixHandler` (не наследник ни `CommandHandler`, ни
`MessageHandler`) и регистрация в `post_init` тестом не покрыты. Конвенция
репозитория — только `CommandHandler` в `register_handlers`; если появится
исключение, тест нужно расширять вместе с ним.

### D7. Правила плана в карточке собираются из констант

`HELP_PLAN_RULES` не пишется текстом «1–2 отдых, 3 — 70 %», а собирается из
`REST_MAX_SCORE`, `LIGHT_SCORE`, `REDUCTION_PERCENT`, `DURATION_STEP_MIN`,
`MIN_DURATION_MIN` из `core/plan.py`.

**Почему:** карточка обещает правило. Если правило поменяют в `plan.py` (например,
60 % вместо 30), текст обязан измениться вместе с ним. Тест на текст, написанный
руками, этого не поймает — он проверяет сам себя.

**Альтернатива (отвергнута):** оставить текст и добавить тест «в карточке есть
слово 70 %». Тест продолжит проходить после изменения правила — то есть будет
охранять опечатку, а не правду.

### D8. Подсказка про фразы-триггеры есть в карточке

`HELP_TRIGGER_HINT` — три фразы, которые показываются в карточке; полный набор
из семи живёт в `HELP_TRIGGERS`. Тест проверяет, что подсказка — подмножество
триггеров.

**Почему не все семь:** «помощь», «help», «какие команды» в тексте — шум. Но
человек, который не помнит команд, должен узнать из карточки, что можно просто
написать «помоги».

## Risks / Trade-offs

- **[Фраза-триггер украдёт запрос у модели]** → только полное совпадение
  нормализованной строки; похожие фразы уходят в ассистент (сценарий R-29).
- **[Карточка разойдётся с кодом при добавлении команды]** → `COMMANDS` как
  единственный источник + тест на дрейф в `build_application`.
- **[Справка обещает несуществующее]** → раздел ограничений, ручная проверка при
  каждом change, который добавляет функцию.
- **[Триггер сработает на «помощь» в другом смысле]** → список фиксированный и
  короткий; расширять только по реальным случаям, а не заранее.
- **[Длинная карточка не влезет в одно сообщение]** → сейчас ~1050 символов,
  лимит Telegram 4096; если вырастет, разделим на два сообщения отдельным change.

## Migration Plan

Схема БД не меняется. Откат — убрать регистрацию двух команд и ветку справки в
`on_free_text`; остальное продолжит работать.

## Open Questions

- Нужны ли кнопки в карточке («показать расписание», «поставить оценку») — решаем
  после недели использования, на требования не влияет.
- Нужна ли подсказка по отдельной команде (`/help new`) — сейчас нет: карточка
  короткая, восемь команд помещаются целиком.
