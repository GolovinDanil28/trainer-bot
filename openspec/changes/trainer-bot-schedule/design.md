# Design

## Context

Репозиторий пока не содержит кода: `src/` и `tests/` создаются этим change'ем.
Ограничения, которые задают подход:

- домен не знает про Telegram (AGENTS.md, п. 8.1), поэтому расписание, вычисление
  моментов и отметки должны работать без сети;
- время хранится в UTC, форматируется в таймзоне пользователя (п. 8.4);
- повторная отправка при рестарте запрещена (п. 8.5) — значит уникальность живёт
  в БД, а не в памяти процесса;
- MVP на одного пользователя, поэтому owner id и таймзона — конфигурация, а не
  таблица.

## Goals / Non-Goals

**Goals:**

- Работающий цикл «команда → БД → напоминание → отметка → журнал» целиком.
- Возможность тестировать поведение без Telegram и без реального времени.
- Ошибки ввода и сбои API не приводят к тихой потере напоминания.

**Non-Goals:**

- Миграции схемы (Alembic) — в v1 таблицы создаются при старте.
- Retry с экспоненциальной задержкой, очередь, отдельный воркер.
- Мультипользовательский режим, часовые пояса на пользователя.
- Чек-ин самочувствия и генерация плана — следующий change.

## Decisions

### D1. Слои: `core/`, `db/`, `bot/`, `scheduler/`

`core/` — чистые функции и dataclasses (вычисление наступивших моментов,
разбор команд, форматирование текста). `db/` — модели и сессии SQLAlchemy.
`bot/` — хендлеры python-telegram-bot. `scheduler/` — тик и вызовы `core/` + `db/`.

**Почему:** большая часть требований (R-01, R-04, R-06, R-08) проверяется на
чистых функциях с фиксированным `now`, а хендлеры остаются тонкими.

**Альтернатива (отвергнута):** писать логику прямо в хендлерах. Быстрее на старте,
но тогда для проверки R-04 и R-06 понадобился бы реальный бот и реальное время —
это ровно тот тип тестов, который через месяц перестают запускать.

### D2. Планировщик — интервальный тик, а не job на каждое напоминание

APScheduler запускает job каждые 30 секунд. Тик спрашивает БД: «какие расписания
попадают в окно `[now, now + 30s)`», и для каждого пытается вставить запись
напоминания.

**Почему:** истина о будущих напоминаниях хранится в БД (`schedule`), а не в
памяти планировщика, поэтому рестарт ничего не теряет (R-10). Пустой прогон стоит
один дешёвый `SELECT`.

**Альтернатива (отвергнута):** `JobQueue` из python-telegram-bot или
`add_job(..., 'date')` на каждый момент. Состояние живёт в памяти процесса,
после рестарта jobs нужно восстанавливать вручную, а тестировать это без
реального ожидания нельзя.

### D3. Модель данных

```
workout    id, type, title, duration_min, is_active, created_at
schedule   id, workout_id → workout.id, weekday (0=Пн..6=Вс),
           time_of_day ('HH:MM', локальное), is_active
           UNIQUE(workout_id, weekday, time_of_day)
reminder   id, workout_id → workout.id, scheduled_at (UTC, ISO),
           status ('pending'|'sent'|'answered'|'missed'),
           attempts (int, default 0), sent_at, created_at
           UNIQUE(workout_id, scheduled_at)
checkin    id, reminder_id → reminder.id UNIQUE, status ('done'|'skipped'),
           created_at
```

`checkin.reminder_id` уникален: одна отметка на одно напоминание — это и есть
механика R-12, без дополнительных проверок в коде.

**Почему `time_of_day` строкой:** расписание недельное и повторяющееся; хранить
конкретный UTC-момент в `schedule` пришлось бы пересчитывать после каждого
перехода на летнее время. Момент вычисляется на лету и фиксируется в `reminder`.

### D4. Идемпотентность — уникальный ключ вместо флага «уже отправлено»

Тик делает `INSERT ... ON CONFLICT DO NOTHING` в `reminder`. Если вставка
состоялась (rowcount = 1), этот проход «владеет» напоминанием и отправляет
сообщение. Если нет — момент уже обработан, проход молча пропускает.

**Почему:** проверка «а не отправляли ли уже» через `SELECT` перед `INSERT`
оставляет окно гонки между двумя тиками; уникальный индекс закрывает его на
уровне БД.

**Альтернатива (отвергнута):** хранить `last_sent_at` в `schedule` и сравнивать с
`now`. При рестарте в ту же минуту это даёт дубль (R-06, сценарий 2), а история
отправок теряется.

### D5. Порядок «вставить → отправить → обновить статус»

Запись создаётся со статусом `pending`, после успешной отправки — `sent`. Если
процесс упал между этими шагами, запись останется `pending`; тик-уборщик
переводит `pending` старше окна ожидания в `missed`, чтобы пользователь не видел
«тишину» как норму. Ретраев в v1 нет — только три попытки внутри одного окна
(R-09).

**Почему так, а не «отправить, потом записать»:** обратный порядок даёт дубли при
падении, а они заметнее и раздражают сильнее, чем пропуск.

### D6. `callback_data` — только `reminder_id` и действие

Формат `ci:<reminder_id>:<done|skip>`. Хендлер загружает напоминание по id,
проверяет владельца и отсутствие существующей отметки, затем вставляет `checkin`.

**Почему не передавать тренировку и дату в кнопке:** данные в кнопке можно
подделать, а id проверяется по БД. Плюс короткий `callback_data` не упирается в
лимит Telegram.

### D7. Конфигурация

`.env` + `pydantic-settings`: `BOT_TOKEN`, `OWNER_ID`, `TZ` (по умолчанию
`Europe/Moscow`), `MISS_WINDOW` (по умолчанию — до конца суток), `DB_URL`.
Таймзона валидируется при старте через `zoneinfo`, чтобы опечатка падала сразу,
а не в момент первого напоминания.

## Risks / Trade-offs

- **[Падение между `INSERT` и отправкой → напоминание не уходит]** → уборщик
  переводит «зависшие» `pending` в `missed`, факт виден в `/history`.
- **[Переход на летнее время: 02:30 существует дважды или не существует]** →
  неоднозначные моменты сдвигаются на час вперёд, это записывается в лог;
  в сценарии R-04 проверяется обычное время 19:30.
- **[SQLite и потоки планировщика + бота]** → одна фабрика сессий, `check_same_thread=False`,
  WAL-режим; короткие транзакции, без долгих блокировок.
- **[Тик 30 секунд = напоминание может опоздать на полминуты]** → окно тика
  сравнивается с `[now - 30s, now + 30s)`, опоздание ограничено одним тиком;
  для тренировок это приемлемо.
- **[Telegram API недоступен]** → три попытки внутри окна, затем `missed` и
  запись в лог (R-09), цикл не останавливается.

## Migration Plan

Greenfield. Таблицы создаются через `Base.metadata.create_all` при старте.
Откат — удалить файл SQLite (данных, которые нужно сохранять, в v1 нет).
Переход на Alembic — отдельным change'ем, когда схема начнёт меняться.
